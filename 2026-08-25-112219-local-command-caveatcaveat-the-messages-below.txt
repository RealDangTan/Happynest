  Keep — these are genuinely good:

  - The HITL boundary table (auto: collect/classify/cluster/summarize/trend ·
    approve: escalate P0/P1, assign owner, create ticket, close issue). This is
    the correct philosophy and maps cleanly onto your existing roles.

    timestamp each stage transition).

  Dangerous if treated as spec:

  1. "7 agents" is narrative inflation. Classification, dedup/clustering, trend
     detection are deterministic functions, not agents — they don't deliberate,
     they compute. If you build 7 LLM-driven agents on a ≤1500-row dataset with
     budget-limited credits, you get 7× cost, 7× latency, 7× failure modes, and
     near-zero accuracy gain. Reframe as: one system, 7 capabilities, exactly 
     2–3 places where an LLM decides anything.
  2. Integration fantasy. Zendesk/Jira/Slack APIs don't exist here. Your real
     inputs are CSV import + manual POST; your real output must be draft 
     artifacts (a rendered ticket text to copy into Jira, a Slack message draft)
     behind an approval button. The story should be rewritten around that, or
     the gap between story and demo will be visible at the defense.
  3. Unspecified math presented as fact. "+238% vs 7-day baseline" needs an
     actual formula — e.g., z-score of today's cluster volume against a trailing
     14-day mean/std per topic. This must be pure code, decided before the LLM 
     ever sees the number. Never let an LLM "judge" trends it can't compute.
  4. The anecdotes secretly require data fields you don't have yet. The
     Google-OAuth story needs per-customer tenant/segment metadata; the
     CSAT-drop pattern needs per-user satisfaction history; "after v2.17" needs
     a release timeline; the 16:00 impact check needs action lifecycle
     timestamps (shipped-fix date, status). Your synthetic dataset generator 
     must emit all of these columns, or none of those demo moments can exist.
     This is the most concrete, most overlooked requirement in the whole doc.
  5. It contains zero failure modes beyond one anecdote — no idempotency, no
     retry, no partial-batch behavior. Fine as vision, unusable as plan.

  Critique: example-agent-flow.mmd

  Good skeleton — shared state, tool use, critic, risk gate, observe-loop are
  all the right vocabulary. Specific problems:

  1. ROUTER{LLM chooses next action} on every step is the wrong default. One
     extra LLM call per step, non-deterministic replays, miserable debugging.
     Look at the edges honestly: after INPUT you always classify; after classify
     you always cluster. Those edges are knowable at build time. A router earns
     its cost in exactly one place (more below).
  2. Two unbounded loops with no terminal condition: CRITIC -->|No| AGENT and
     OBSERVE --> STATE. Nothing caps iterations; nothing guarantees END. Add
     max_iterations and explicit exit edges.
  3. Internal contradiction with the story: the low-risk branch of RISK
     auto-executes "Update Status" — but the story says closing an issue
     requires approval. Pick one boundary table and derive both the diagram and
     the story from it, or the examiner will catch the inconsistency.
  4. State is conflated with persistence. "Shared VoC State" mixes two things
     that must live differently:
     - Working memory → LangGraph state + Postgres checkpoints (resumability —
       S5 territory)
     - Durable artifacts (clusters, insights, decisions, actions) → normal 
       business tables, because your future Next.js dashboard must render them
       without ever replaying a graph.
  5. Missing entirely: error/retry branches, idempotency (what happens when the
     same batch runs twice?), and a trigger model — the story implies a
     continuous daemon ("8:30 dashboard"), but at your scale the honest answer
     is a batch run over "feedback created since last watermark."

  ---

  My recommended shape: pipeline spine + bounded agentic investigation

  [batch trigger] → fetch new feedback since watermark
    → classify/embed        (already built upstream)
    → cluster               (deterministic: pgvector kNN + connected components,
  no ANN index needed at ≤1500)
    → trend/spike compute   (deterministic z-score math)
    → for each flagged cluster:
         INVESTIGATE  ← the ONLY agentic loop, capped at K tool calls
           tools: retrieve similar past insights (+ their human decisions!)
                  query metrics, pull representative quotes
         SYNTHESIZE insight + evidence
         CRITIC = deterministic sufficiency checklist (size ≥ N, users ≥ M,
                  confidence ≥ t, has quotes) + max ONE LLM reflection pass
    → risk gate (rule-based whitelist, NOT an LLM judgment)
    → LangGraph interrupt → human approves/edits/rejects
    → execute = generate draft artifact → log decision as precedent
  [closed-loop job, separate & lightweight]: re-check clusters touched by
    shipped actions N days later → before/after volume + CSAT delta

  Why this split wins for the thesis:

  - The agentic claim survives — "agent autonomously investigates emerging
    clusters using tools" is real and demonstrable — while 90% of execution
    stays deterministic, cheap, and reproducible.
  - Precedent-aware prioritization falls out almost for free: store human
    decisions on past insights, embed insight summaries, retrieve via your
    existing embedder + pgvector pattern. That's the story's best moment,
    implemented with zero new infrastructure.
  - The critic-as-checklist is defensible ("we verify evidence sufficiency with
    measurable criteria") versus a vibes-based LLM reflection loop.
  - Cost is bounded by construction: K tool-call budget × number of flagged
    clusters per batch.

● Sharp question — and the honest answer is: you need the "R", you're already 
  building it, but calling it "RAG" would undersell what's actually happening.
  Let me split the hair properly.

  Where classic RAG does NOT apply

  Classic RAG = user question → embed query → vector-search an external document
  corpus → stuff top-k chunks into the prompt → hope they contain the answer.
  That pattern fits chatbots over PDFs. Your system is different in three ways:

  1. Your corpus is your own database, ≤1500 structured rows you fully control —
     not unknown external documents.
  2. Grounding is enforced by schema, not by hope. Every insight must carry
     evidence_ids pointing at exact feedback rows. Classic RAG "usually
     retrieves relevant chunks"; your design mandates citations — the LLM cannot
     emit an insight without source IDs. That's stronger than RAG's grounding.
  3. Retrieval is a decision, not a reflex. In a RAG pipeline every query
     triggers retrieval. Here the router decides whether it needs historical
     context (retrieve_similar_insights) or just SQL metrics. Auto-stuffing
     top-k into every prompt would burn budget and blur the temperature=0
     determinism you locked.

  Where retrieval genuinely appears in your system

  RAG concept: Vector search
  Your equivalent: Similar feedback lookup
  Mechanism: Already live: pgvector kNN, /feedbacks/{id}/similar (phase 08)
  ────────────────────────────────────────
  RAG concept: RAG over past decisions
  Your equivalent: Precedent retrieval — "a similar cluster was rated P2 last
  month"
  Mechanism: retrieve_similar_insights: embed insight summaries, kNN against new

  cluster summary → inject precedents into prioritization prompt
  ────────────────────────────────────────
  RAG concept: Grounded generation
  Your equivalent: Insight synthesis
  Mechanism: fetch_evidence_quotes(cluster_id) pulls sanitized quotes; schema
  forces evidence_ids
  ────────────────────────────────────────
  RAG concept: Retrieval-augmented classification
